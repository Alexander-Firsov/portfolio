# 🌐 Инфраструктурный кейс: Развертывание веб-портала Django в оркестраторе Docker Swarm с Ingress-маршрутизацией (Traefik)

**HASH2FILE** — микропроект, демонстрирующий построение изолированной, отказоустойчивой инфраструктуры для веб-приложений и СУБД на базе оркестратора Docker Swarm. 

**Инженерный контекст:** Проект был успешно мигрирован со стандартного Docker Compose после критических сбоев и нестабильной работы проприетарных веб-служб Synology NAS.

---

## 🛠️ Архитектурный стек

* **Оркестрация и контейнеризация:** Docker Swarm (Overlay-сети, декларативное управление репликами, ограничения размещения сервисов).
* **Маршрутизация и Безопасность (Ingress):** **Traefik** в качестве глобального Edge-роутера, автоматический выпуск и продление SSL-сертификатов Let's Encrypt (HTTP-01 challenge), Middleware для честного 301-редиректа (HTTP -> HTTPS).
* **Backend:** Django (WSGI-сервер Gunicorn, изоляция окружения внутри контейнера через `.venv`).
* **Database:** **PostgreSQL 17.4-alpine** с интегрированным автоматическим Healthcheck (`pg_isready`).
* **Web/Static:** Nginx для эффективной отдачи статических данных и медиафайлов.

---

## 🏗️ Ключевые инфраструктурные и сетевые решения

1. **Эшелонированная сетевая изоляция:** Контур безопасности разделен на две изолированные overlay-сети:
   * `public-ingress` (внешняя сеть) — доступна только для связи Nginx с глобальным балансировщиком Traefik.
   * `default` (внутренняя сеть стека) — полностью изолирует трафик между Django и PostgreSQL от внешней среды, исключая несанкционированный доступ к СУБД.
2. **Декларативное управление Ingress-трафиком:** Вся логика маршрутизации, конфигурация SSL-резолвера (`le-ssl`) и правила перенаправления портов (80 -> 443) вынесены в `labels` сервиса Nginx. Это позволяет масштабировать веб-часть без изменения глобального конфига прокси.
3. **Управление состоянием (State) в условиях локального хранения:** Из-за специфики аппаратной платформы (одиночный NAS-сервер) применено жесткое связывание контейнеров с Master-нодой с помощью директивы `placement.constraints (node.role == manager)`, что гарантирует консистентность данных PostgreSQL и медиафайлов на локальных томах `/volume1`.

---

## ⚠️ Текущие компромиссы и точки развития стека

* **Обработка готовности СУБД:** В силу ограничений Docker Swarm, стандартная директива `depends_on` контролирует только порядок запуска, но не фактическую готовность СУБД к приему соединений. Для предотвращения падения Django при «холодном» старте планируется внедрение кастомного `entrypoint.sh` с проверкой доступности порта СУБД.
* **Масштабирование хранилища:** Для перехода к полноценному горизонтальному масштабированию (добавление Worker-нод) планируется миграция с локальных папок `/volume1` на распределенную файловую систему (NFS с TLS-шифрованием трафика).

## 🚀 Эксплуатационные команды

**Развертывание/Обновление всего стека служб:**
```bash
sudo docker stack deploy -c docker-compose.yml h2f
```

**Ручная сборка образов (актуально для Swarm, так как он игнорирует секцию `build` при деплое):**
```bash
docker compose build --no-cache django
```

**Остановка и удаление стека:**
```bash
sudo docker stack rm h2f
```
